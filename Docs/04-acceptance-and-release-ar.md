# اختبارات القبول والإطلاق — واجهة خزائن جاهز

اقرأ [فهرس الحزمة](README.md) أولاً. هذه قائمة تنفيذ وتسليم للواجهة وليست ادعاء بأن اختبارات الإنتاج اكتملت.

## 1. ترتيب العمل المقترح

1. إضافة العقود والعميل وربط الجلسة والصلاحيات ومعالجة ProblemDetails.
2. الحسابات والأرصدة والدفتر، مع أسماء الأشخاص والشركات وإخفاء المعرفات.
3. التمويل والتحويل والقبض/الصرف ونماذج التسويات المخولة.
4. التسليم: المعاينة، التقديم، العد الفعلي، التأكيد، الإلغاء، والقفل.
5. بترو آب: أدلة التمويل والبيان والاستبدال والمطابقة.
6. التقارير الخمسة وتنزيلات الخادم، ثم تحديث شاشات V2.
7. أدوات الترحيل المخولة، إن كانت ضمن نطاق فريق الواجهة، مع اختبار على بيئة مالية مخصصة.

في كل مرحلة افحص الصلاحيات والحالات الفارغة والأخطاء والتزامن، ثم انتقل للمرحلة التالية. لا تنتظر اكتمال التصميم لبدء مطابقة أسماء الحقول والعقود.

## 2. بيانات اختبار مطلوبة

أنشئ في بيئة اختبار حسابات جاhez لكفلاء مختلفين، ومندوباً كفيل وظيفته مختلف عن كفيل الحساب، ومستخدم مشرف ومستخدم محاسب منفصلين، وأدواراً بصلاحيات قراءة فقط وبدون تصدير وبدون تسوية. استخدم رصيداً موثقاً للكفيل الأول ورصيداً منفصلاً للثاني، ورسماً مدفوعاً جزئياً، وديناً مرحلاً، ومحاضر معلقة ومؤكدة وملغاة، وأدلة بترو آب مكتملة وناقصة.

الأسماء في هذه البيانات عربية واضحة. لا تستخدم GUID كاسم مستخدم في لقطة تسليم أو ملف عينة. احتفظ بالمعرفات داخل بيانات التكامل اللازمة فقط. لا تنفذ سيناريوهات الأموال أو الترحيل على الإنتاج للتحقق من الواجهة.

## 3. مصفوفة القبول المالي والواجهة

| الحالة | النتيجة المطلوبة |
|---|---|
| كفيل حساب جاهز مختلف عن كفيل الموظف | المعاينة والحركة تعرضان كفيل الحساب؛ لا يختار المتصفح كفيل الموظف |
| تغيير كفيل الحساب بعد إنشاء التزام رسوم | الدفعات اللاحقة تبقى للكفيل الأصلي، والتاريخ لا يتغير |
| تغيير الكفيل بعد إعداد عملية تصفية | رفض التنفيذ القديم، وإعادة تحميل وتحديث العملية ومعاينتها |
| سداد دين بعد تغيير الكفيل | اسم الكفيل الأصلي ومصدر الدين محفوظان |
| وجود رصيد لكفيل آخر فقط | الصرف مرفوض؛ لا يعرض نجاحاً أو يقترح تغطية تلقائية |
| وجود رسوم فقط بدون تمويل تصفيات | الصرف من عهدة التصفيات مرفوض |
| رصيد ظاهر لكنه محجوز لتسليم معلق | تظهر رسالة الخادم، ولا يسمى الرصيد «متاحاً للصرف» |
| تحويل داخلي | أثران متعاكسان للكفيل نفسه، دون إيصال أو إيراد جديد |
| محاولة خروج مباشر من عهدة المشرف | الواجهة توجه للتسليم، والخادم يرفض التحويل اليدوي |
| محاولة تمويل عهدة الرسوم أو مقاصة بترو آب | غير متاح كاختيار صالح، مع معالجة رفض الخادم |
| عرض أرصدة الأب والأبناء | لا يضاعف مجموع البطاقات |
| فشل تحميل الأرصدة | حالة خطأ، وليس رصيداً صفرياً |
| V2 funds مع V3 balances | قسمان واضحان: نشاط غير مسلم ورصيد فعلي |

## 4. التسليم والعد والتزامن

- [ ] المعاينة حتى نهاية يوم الرياض المختار تشمل العهدة السابقة غير المسلمة.
- [ ] تعتمد شاشة التفاصيل نسخة التقديم المرجعة، ولا تواصل عرض أرقام معاينة أقدم.
- [ ] فصل كل كفيل والغرضين، مع البنك وبترو آب خارج النقدية الفعلية.
- [ ] لا يملأ التطبيق النقدية الفعلية تلقائياً على أنها معدودة.
- [ ] لكل سطر نقدي حقل مستقل، بما فيه الصفري، وترسل السطور نفسها مرة واحدة.
- [ ] فرق موجب في سطر وسالب في آخر يمنع التأكيد، حتى إذا تطابق الإجمالي.
- [ ] لا يوجد شطب تلقائي أو اعتماد جزئي عند الفرق.
- [ ] مقدم المحضر لا يعتمد محضره بنفسه؛ الإلغاء للمقدم فقط وهو معلق.
- [ ] طلب معلق موجود يمنع تقديم طلب آخر؛ تعرض الواجهة المحضر القائم.
- [ ] تسجيل حركة بعد التقديم لا يغير المحضر ولا يمحو تلك الحركة بعد التأكيد.
- [ ] تأكيد من نافذتين لا ينتج تحويلين؛ تستوعب الواجهة نجاح إحداهما وتعاقب حالة الأخرى بإعادة التحميل.
- [ ] اختلاف rowVersion يعالج بتحديث السجل، ولا تعرض نجاحاً قبل استجابة الخادم.
- [ ] انقطاع الشبكة بعد الإرسال يحافظ على المفتاح والمحتوى عند إعادة المحاولة.
- [ ] المؤكد للعرض والطباعة، والملغى لا يمكن تأكيده، والمقفل لا يقبل تصحيحاً يتجاوز سير العمل.
- [ ] لا ينشئ عبور منتصف الليل محضراً أو تصفيراً آلياً.

## 5. بترو آب والتقارير والملفات

- [ ] غياب دليل تمويل أو بيان يعرض «غير متحقق»، لا0.00.
- [ ] دليل حقيقي مسجل بصفر يعرض0.00 بوصفه قيمة معروفة.
- [ ] تكرار مرجع الكفيل يرفض، والواجهة تحتفظ بإدخالات المستخدم لتصحيحها.
- [ ] استبدال دليل ينشئ سجلاً جديداً بمرجع جديد، ويظل الأصل مرئياً تاريخياً.
- [ ] إضافة دليل تمويل لا تنشئ إيصال مندوب آخر ولا تزيد رصيد التحصيل.
- [ ] النطاق الجزئي للشهر لا يظهر استهلاكاً يومياً مستنتجاً من إجمالي الشهر.
- [ ] بيان بداية الفترة يحتاج اليوم السابق تحديداً، وبيان النهاية يحتاج اليوم الأخير.
- [ ] حالة المطابقة تستخدم قيمة الخادم، ولا تتحول إلى متطابق مع نقص دليل.
- [ ] مجاميع التقرير للفترة كاملة مع أن تفاصيل JSON مرقمة.
- [ ] التنزيل يستخدم الفلاتر نفسها ويحتوي كامل النطاق، وليس صفوف الصفحة الحالية فقط.
- [ ] تجاوز10,000 قيد يعرض طلب تضييق الفلاتر؛ لا يحمل ملفاً جزئياً.
- [ ] محضر غير مؤكد لا يطبع كمحضر معتمد.
- [ ] كشف التجارية يثبت كفيل التجارية الصحيح من الخادم.
- [ ] أسماء المشرف والمحاسب والمندوب والمنفذ صحيحة في الشاشة وExcel وPDF.
- [ ] لا يوجد GUID ظاهر في ملف أو اسم بديل لشخص، بما في ذلك نص مرجع تاريخي.
- [ ] تغيير اسم مستخدم لاحقاً لا يستبدل الاسم المحفوظ في اعتماد جديد سابق.
- [ ] PDF عربي مقروء، وRTL سليم، والمبالغ والتواريخ وأرقام المستندات غير مقلوبة.
- [ ] خطأ التنزيل يعرض رسالة، ولا يحفظ ProblemDetails كملف PDF.

## 6. الصلاحيات والربط

- [ ] مستخدم بدون صلاحية القراءة لا يستطيع فتح بيانات الخزينة، حتى برابط مباشر.
- [ ] قراءة التقرير لا تعني صلاحية تصديره؛ الزر يتطلب الصلاحيتين.
- [ ] صلاحية إنشاء حساب لا تمنح التحويل أو تعديل الحساب تلقائياً.
- [ ] Business يحتاج entries.create، والافتتاح والتسوية والعكس تحتاج adjust.
- [ ] يراعى نطاق منصة جاهز، ولا يستخدم اسم الدور بديلاً عن الصلاحية.
- [ ] GET لا ينفذ تفعيل أو ترحيل أو إنشاء سجل مالي.
- [ ] لا تستدعى readiness من مستخدم مشرف بلا صلاحية التسوية.
- [ ] لا يرسل المتصفح sponsorId لتغيير ملكية رسوم أو تصفية V2.
- [ ] ربط الصفحة لا يفترض totalCount أو فلاتر غير مدعومة للمحاضر والأدلة.
- [ ] تاريخ DateOnly يظل اليوم نفسه عند اختلاف إعداد منطقة جهاز المستخدم.
- [ ] الأزرار تمنع النقر المكرر، وعمليات retry تحتفظ بمفتاح الأمر.

## 7. الترحيل والإطلاق

هذه الأدوات لمالية مخولة وبالتنسيق مع فريق الباك إند، وليست wizard ذات قرارات مالية آلية:

1. نشر المخطط والإذن بالخادم بدون تفعيل الخزينة.
2. إنهاء أو إلغاء المحاضر القديمة المعلقة.
3. مراجعة أصل الملكية بأدلة التاريخ؛ الكفيل الحالي للمقارنة فقط.
4. تشغيل backfill على دفعات، مع مفتاح مختلف لكل دفعة جديدة، وبدون تخمين التمويل الناقص.
5. مطابقة كل حساب ترحيل نشط وإثبات الرصيد، بما فيه الصفر؛ أي فروق تحتاج معالجة مالية صريحة.
6. إعادة فحص readiness بعد أي تعديل مالي، ثم تفعيل مقصود من المالية باستخدام النسخة الحالية.
7. تمكين شاشات V3 في إعداد إطلاق الواجهة واستبدال كتابات تسليم V2. إذا رجع `treasury_upgrade_required` اعرض المسار الجديد.
8. بعد بدء القيود، التعافي بقيود تصحيح مدققة، وليس حذف الدفتر أو إخفاء V3 للعودة إلى كتابة تسليم V2.

لا يفترض فريق الواجهة أن استجابة readiness خالية الموانع تعني أن activate لن يراجع شروطاً إضافية. إذا رفض الخادم، اعرض الرسالة وارجع للمراجعة. لا تضف أموالاً افتتاحية لمجرد إخفاء الفرق أو تكرار تحصيل قديم.

## 8. حالة التحقق عند كتابة الحزمة

بناء الحل ناجح، واختبارات جاهز204 ناجحة و16 متخطاة، وFleet1088 ناجحة و23 متخطاة، وفحص TypeScript الصارم ناجح. اختبارات Domain بها282 ناجحة وثلاث حالات فشل سابقة غير مرتبطة بالخزينة. اختبرت حسابات ملفات التقارير، وأُنتجت الأنواع الخمسة وفُحصت أسماء المحضر العربي بصرياً، ولم توجد GUIDs في النص المستخرج من الملفات الخمسة.

اختبارات ضمانات SQL Server الخاصة بالقيود وrowversion والتزامن والمعاملات لا تزال تحتاج خادماً سليماً: LocalDB في البيئة المحلية يتعطل قبل بدء المحرك. لذلك لا تعد الحزمة تصريح إطلاق إنتاج، ولا تعتبر اختبارات InMemory إثباتاً لذرية SQL. [تفاصيل التحقق](../../outputs/jahez-treasury-verification/verification.md) و[دليل التشغيل](../jahez-treasury-v3-ar.md).

## 9. ما يسلمه فريق الواجهة

تسليم PR الواجهة مع الشاشات المرتبطة فعلياً، ونتائج المصفوفة السابقة، ولقطات عربية لعرض الرصيد والتسليم والمطابقة، وعينات تنزيل من بيئة الاختبار. حدد أي قدرة إضافية تحتاج تغيير API بوضوح، بدلاً من افتراض وجودها. لا تضع بيانات اعتماد أو توكنات أو بيانات مالية حقيقية في الوثائق أو اللقطات.
